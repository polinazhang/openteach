DOWNSTREAM EVALUATION CONTRACT
Scope: Cartesian-tag Franka checkpoints trained with the inspected trainer config.
This contract does NOT describe the older joint-tag checkpoints in the same root.
Direct data checks covered franka-30; see verification coverage limitations below.

Training is consistent with ABSOLUTE CARTESIAN POSE prediction. It is NOT training
for delta Cartesian prediction. Converting JAX weights to Torch preserves this.

Physical action layout, AFTER unnormalization (zero-based indices):
  0: target x
  1: target y
  2: target z
  3: target quaternion x
  4: target quaternion y
  5: target quaternion z
  6: target quaternion w
  7: binary gripper command, training values -1 and +1
XYZ and orientation specify the absolute commanded end-effector pose in the
recorder robot interface's pose frame, using its position units. They are not
offsets from current state, chunk-start state, or the preceding action. Rotation
is a quaternion in xyzw order, not wxyz, Euler angles, axis-angle, or a quaternion
increment. Quaternions q and -q represent the same orientation.
Coordinates 8 through 31 are model padding, NOT additional robot commands.
Gripper is a command, not the measured gripper_pos input and not a Cartesian delta.

Output boundary and scaling:
  - Raw model sample_actions output has 50 time steps and 32 coordinates per step
    (plus a batch dimension where applicable). The first eight are normalized.
  - For raw normalized coordinate z_i, recover the stored action with:
      a_i = (z_i + 1) / 2 * (q99_i - q01_i + 1e-6) + q01_i
    using actions statistics from that checkpoint's assets/franka/norm_stats.json.
  - Do not substitute dataset statistics or recompute normalization at evaluation.
  - OpenPI create_trained_policy with the Cartesian training config already applies
    Unnormalize in its output transforms. Do NOT unnormalize those outputs again.
    The inspected Cartesian config has no output slice transform, so this standard
    policy path retains the padded width unless the caller supplies another output
    transform. Inspect the wrapper boundary and consume only the first eight.
  - Predicted values are continuous. Binary training gripper values and unit
    training quaternions do not guarantee exactly binary/unit model predictions.
    Gripper discretization and quaternion normalization/invalid-value handling
    belong to the evaluation adapter and must be explicitly recorded.

Temporal meaning:
  - Each predicted chunk contains targets for t, t+0.05, ..., t+2.45 seconds:
    50 action slots sampled from 20 Hz training data.
  - Every slot is an absolute pose target; do NOT cumulatively sum the slots.
  - Chunk length does not prescribe executing all 50 slots open-loop. Record the
    actual execution horizon, replanning interval, and control rate for comparison.

Input contract for the same training configuration:
  - observation.state is eight values: seven measured joint positions followed by
    measured gripper_pos, in the dataset's original conventions. Do NOT replace
    these with XYZ/quaternion or command values. Apply the checkpoint state stats
    and model preprocessing once, as the standard policy wrapper does.
  - Camera mapping: camera_front -> base_0_rgb;
                    camera_wrist -> left_wrist_0_rgb;
                    camera_side -> right_wrist_0_rgb.
    All three were enabled. FrankaInputs expects observation.images.<camera> keys.
  - Provide the task prompt; use the training image resize/tokenization pipeline.
  - Model architecture: Pi0.5, action_dim=32, action_horizon=50, max_token_len=200.
    Select tag='cartesian' explicitly; the trainer factory defaults to 'joint'.

Environment/controller compatibility:
  - An environment accepting absolute poses must receive the decoded pose in its
    matching frame, units, quaternion convention, and tool frame.
  - An environment accepting deltas must first convert the absolute target against
    the CURRENT measured end-effector pose using that controller's convention.
    Do NOT send these eight absolute values directly to a delta-action interface.
    Do NOT subtract joint observation.state from Cartesian coordinates.
  - The inspected recorder forms translation error and relative-rotation
    axis-angle error, then clips them before sending a six-dimensional arm_action
    to OSC_POSE. Gripper is sent separately. Its source constants are translation
    limit 0.1 and per-axis rotation limit 0.5; these are recorder implementation
    facts, not a verified specification of a different evaluation controller.

Unresolved adapter conventions (do not silently guess):
  - The exact evaluation world's alignment and tool/TCP transform to the recorder
    robot-interface frame, and explicit confirmation of position units.
  - Whether -1 or +1 means open/closed in the evaluation gripper driver, and the
    threshold/mapping for continuous model predictions. The training dataset
    proves the two labels, not a freshly verified driver endpoint mapping.
  - Evaluation controller delta frame, rotation composition, action scaling,
    clipping, and timing. These are not specified by the model architecture.
The model's action representation is specified above; these environment-specific
conventions must be matched and documented before claiming comparable closed-loop
evaluation. This log does not establish policy quality or successful rollouts.

CONCLUSION
The inspected Cartesian training configuration learns the stored eight-dimensional
Cartesian commands, after normalization. It does not construct Cartesian deltas.
The inspected data and recorder evidence indicate ABSOLUTE Cartesian pose targets,
not the delta controller actions described in the request.
The configuration's absolute_cartesian_xyz_quaternion_xyzw metadata agrees with
this evidence. My earlier suggestion to relabel it as delta was premature.

If the dataset really contained deltas, passing them through would preserve those
deltas. That conditional statement is correct, but is not evidence that this
dataset contains them. The source recorder distinguishes two different fields.

  Pi0.5 uses quantile normalization, image resizing, prompt/state tokenization,
  and state/action padding.
src/openpi/transforms.py, Normalize/PadStatesAndActions:
  normalized action = 2 * (stored action - q01) / (q99 - q01 + 1e-6) - 1.
  No clipping is performed by this normalization.
  Eight normalized action coordinates are padded with 24 zeros.
  Training target shape per example is (50, 32).
scripts/train.py and src/openpi/models/pi0.py:
  These processed actions feed the flow-matching loss directly; the loss does not
  reinterpret them as Cartesian deltas. Metadata does not change the loss targets.
